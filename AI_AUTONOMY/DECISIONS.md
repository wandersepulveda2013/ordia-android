| 2026-08-10 | El workflow verifica contra la API de Jules que la rama `jules/autonomous-ordia` exista en el source ANTES de lanzar; si no, el ciclo se omite (no falla el job). | La rama nueva puede tardar en sincronizarse con el conector de Jules; lanzar contra una rama inexistente fallaría en la sesión. | Primeros ciclos pueden ser no-op hasta que Jules vea la rama. |
| 2026-08-10 | Cron cada 2 horas en el minuto 17 (`17 */2 * * *`). | Suficiente para progreso continuo sin saturar CI; evita el minuto 00 y reduce colisión con otros jobs; `workflow_dispatch` permite arranque manual. | Ventana de oportunidad cada 2h. |
| 2026-08-10 | LA INFRAESTRUCTURA DE ORQUESTACIÓN VIVE EN `main`: `.github/workflows/ordia-autonomous-jules.yml` (scheduler), `.github/workflows/ordia-autonomous-merge.yml` (auto-merge) y `.github/workflows/android-ci.yml` (CI) se publican en `main` porque GitHub Actions ejecuta los schedulers desde la default branch. | El workflow nuevo NO estaba en `main` (solo en la rama autónoma) → el cron no corría. | Scheduler y auto-merge activos desde `main`; el código del rebuild sigue en `jules/autonomous-ordia` y NO se mergea a main. |
| 2026-08-10 | Auto-merge real y restringido: nuevo workflow `ordia-autonomous-merge.yml` mergea (squash, sin force) PRs hacia `jules/autonomous-ordia` cuando pasan 12 guardas (base exacta, no-main guard clause, no fork + patrón de rama Jules, no draft, mergeable, checks success, security checks success). | `AUTO_CREATE_PR` crea la PR pero NO la mergea; el session lock antiguo (cualquier PR abierta → no lanzar) habría bloqueado la autonomía indefinidamente. | PRs autónomas se fusionan solas tras CI verde; el humano NO tiene que mergear cada PR de Jules. |
| 2026-08-10 | El session lock distingue estados: sesión activa (API Jules) → skip; PR fallida → `proceed_with_failure_context` (la nueva sesión recibe el fallo); CI corriendo → `skip_ci_running`; PR lista → `skip_ready_for_merge`; ≥4 PRs → `skip_too_many_prs`; mismo área fallada ≥2 veces → `loop_warning`. | El lock antiguo (una PR abierta bloquea todo) era demasiado burdo y detendría el progreso tras la primera PR. | La autonomía continúa corrigiendo regresiones reales en lugar de detenerse. |
| 2026-08-10 | Jules NUNCA auto-mergea hacia `main`; el auto-merge tiene guard clause explícito (`base_ref == "main"` → MERGE PROHIBIDO) además de requerir base exacta `jules/autonomous-ordia`. | Proteger la base estable de cambios no revisados por humanos. | Sin camino automático `* → main`; solo el humano decide si algo llega a main. |
| 2026-08-10 | CI cubre también PRs hacia `jules/autonomous-ordia`: `android-ci.yml` ampliado (`branches: [main, jules/autonomous-ordia]`). | Los checks de la rama head solo existen si el workflow está presente; sin CI en las PRs autónomas el auto-merge esperaría forever. | Cada PR de Jules corre verify (tests+lint+assemble); sign/publish solo en push a main. |
| 2026-08-11 | La verificación del dominio en entornos sin Android SDK se hace con kotlinc + JUnit4 + stubs (`tools/domain-smoke/RoomStubs.kt`, `PreferenceStubs.kt`), no con gradle. | `./gradlew test` requiere Android SDK no siempre disponible; el dominio es Kotlin puro (java.time, kotlinx, org.json) y sus tests solo dependen de `data.local` (Room, con stubs) y `data.preferences` (DataStore, con stubs). | Baseline de dominio reproducible en JVM pura (125 tests + 25 smoke assertions). Los tests que necesitan DAOs/Context/RoomDatabase (backup, context, repositories) quedan fuera de esta baseline y requieren Android SDK o Robolectric. |
| 2026-08-11 | El smoke de dominio (`tools/domain-smoke/DomainSmoke.kt`) debe usar el set explícito de kinds core alimentados, NO `SearchKind.entries.toSet()`. | `SearchKind` creció a 7 valores (CONVERSATION/COMMITMENT/AUTOMATION añadidos) pero el smoke solo alimenta 4 listas; `entries.toSet()` es un bug obsoleto que nunca pasaría. | Smoke alineado con `SearchEngineTest`; `run_domain_checks.sh` vuelve a ser verde. |
| 2026-08-11 | `NoteBlockCodec.decode` debe ser resiliente por elemento, no por array completo: el `runCatching` no puede envolver todo el bucle de parseo porque un único elemento malformado causaría pérdida total de bloques. | Data loss silencioso P1: un elemento corrupto (string donde se esperaba objeto) hacía que toda la nota se colapsara a un párrafo vacío/fallback. La codificación nunca produce tales elementos, pero restauraciones externas o futuras extensiones podrían. | El array raíz se valida por separado (corrupción total → fallbackBody); dentro del array, los elementos malformados se descartan y los válidos se conservan; solo si todos fallan se cae al fallback. 11 tests cubren el comportamiento. |
| 2026-08-11 | Se estandariza `tools/run_domain_tests.sh` como runner JUnit4 reutilizable (compila stubs + dominio + tests, ejecuta con `JUnitCore`) para todas las sesiones autónomas sin Android SDK. | La sesión anterior corrió 136 tests con un comando ad-hoc no persistido; sin script reusable, cada sesión reconstruiría la classpath/stubs. | 147 tests se ejecutan con `bash tools/run_domain_tests.sh` desde cualquier sesión; la baseline de dominio es reproducible y extensible. |
| 2026-08-11 | **Modo continuo**: se adopta un supervisor persistente (`tools/ordia_supervisor.py`) como orquestador único de la Automation `Ordía Continuous Evolution`, en lugar del cron. | El cron cada 2h dejaba huecos de hasta 2h (no es continuidad real). Además, el cron dispatcha ciegamente sin comprobar runs activos → se detectaron 2 runs concurrentes (viola MAX_CONCURRENT=1). El automation service NO previene solapamiento. | El supervisor (ejecutado en una máquina siempre encendida del usuario) comprueba runs activos vía API y solo dispatcha cuando no hay ninguno (MAX_CONCURRENT=1 garantizado); encadena el siguiente run en ~15–40 s. Deshabilita el cron al arrancar y lo rehabilita al detenerse (watchdog de seguridad). Sin supervisor, el cron cada 15 min es modo degradado. Timeout de la automation subido 600→1800 s (los runs "FAILED" por timeout sí commiteaban antes de morir). Rama de trabajo: `openhands/autonomous-ordia` (memoria Git persistente de OpenHands, separada de `jules/autonomous-ordia`). |
| 2026-08-11 | **Supervisor v2**: lock cross-platform (fcntl/msvcrt/pidfile), lease distribuido vía GitHub Gist con TTL, y watchdog GitHub Actions externo. | v1 dependía de `fcntl` (solo Unix), rehabilitaba el cron solo en `finally` (irrecuperable si `kill -9`/apagón), y no tenía lock distribuido (supervisor + watchdog + cron podían pisarse). | Lock funciona en Linux/Windows/WSL. El lease expira automáticamente (TTL 300s) sin depender de `finally`, así el watchdog GitHub Actions detecta un supervisor muerto y rehabilita el cron + dispatch recovery. Concurrencia=1 garantizada en 3 niveles (API check, lock proceso, lease+watchdog). Cloud-first: docker/systemd/install permiten apagar el PC. |
| 2026-08-11 | **Continuous Delivery dedicado a `openhands/autonomous-ordia`** con naming exacto del auto-updater, en lugar de reutilizar `android-ci.yml`. | `android-ci.yml` publicaba releases con tag `v3.0.0-build.N` y asset `Ordia-3.0-signed.apk`, pero `UpdateSecurityRules` exige `v3.0.N-code-C` y `Ordia-3.0-code-C.apk` → el auto-updater nunca detectaba la actualización (funcionalidad falsamente implementada). Además no disparaba en la rama autónoma. | `openhands-delivery.yml` produce artifacts que el updater SÍ consume end-to-end: tag `v3.0.{run_number}-code-{versionCode}`, asset `Ordia-3.0-code-{versionCode}.apk` + `.sha256`, no-prerelease, gates tests+lint+assemble, concurrency cancela obsoletas, no sobrescribe releases existentes. |
| 2026-08-13 | **Dos FileProviders vía subclase dedicada (`UpdateFileProvider`)**, no dos `<provider>` con el mismo `android:name`. El manifiesto `main` declara `${applicationId}.attachments` (adjuntos); los flavors `previewAdvanced`/`previewFull` declaran `${applicationId}.update-files` (auto-update). Ambos usaban `android:name="androidx.core.content.FileProvider"` → el manifest merger los fusiona por `android:name` y colisiona en `authorities`/`resource` → `processPreviewAdvancedDebugMainManifest` FAILED, lo que bloqueó TODOS los releases del delivery durante ~12 runs consecutivos. | El merger de AGP trata elementos con el mismo `android:name` como un único elemento lógico: dos FileProviders con distinta authority pero mismo nombre NO coexisten. La forma correcta y estándar de tener dos FileProviders es darles `android:name` distintos, lo que requiere una subclase. | Creada `app/src/main/java/com/ordia/app/updates/UpdateFileProvider.kt` (`class UpdateFileProvider : FileProvider()`); los dos manifests de flavor referencian `.updates.UpdateFileProvider`. El call site `OrdiaUpdateManager` resuelve URIs por authority string en runtime (independiente de la clase), sin cambio de código. Verificado localmente con Android SDK: clean+test (3768 tests, 0 failures)+lint+assemblePreviewAdvancedRelease BUILD SUCCESSFUL; manifest merge verde para las 3 variantes. Tras el push, run 31735618004 success → release `v3.0.80-code-1300008001` publicada. Lección: cualquier nuevo FileProvider DEBE usar una subclase propia si ya existe otro FileProvider en el manifiesto. |
| 2026-08-13 | **Delivery `cancel-in-progress: false`** (era `true`). El bucle autónomo empuja commits cada ~3 min y la build de delivery tarda ~10 min; con `cancel-in-progress: true` cada push cancelaba la build en curso, de modo que ninguna build finalizaba y las mejoras de los ciclos 51-57+ no se publicaban (última release quedó estancada en ciclo ~50). | `cancel-in-progress: true` es útil para no desperdiciar CI cuando los pushes rápidos hacen obsoletas las builds, pero cuando la cadencia de pushes (~3 min) supera la duración de la build (~10 min), cancela TODAS las builds y el canal de release queda mudo. La prioridad es que las mejoras se publiquen, no ahorrar minutos de CI. | Con `cancel-in-progress: false`, la build en curso completa y publica su release; el push más reciente queda pendiente (queued) y corre después. GitHub mantiene a lo sumo 1 job pendiente por grupo (los pushes intermedios se reemplazan entre sí), así no hay cola infinita. Verificado: run de ciclo 57 (053e7ff) success → release `v3.0.93-code-1300009301`; builds posteriores (e611da6, db30b9c) quedan pending/in_progress en vez de cancelled. El canal de release vuelve a avanzar. |
